## 一、SQL里的那一行

问题最终定位到一段核心代码：

```sql
select  a.enter_id
    ,   min(if(event = 'shop_comment_show', time, null)) as shop_comment_show_earliest_time
from (
    select  enter_id, min(time) as time
    from    log_table
    where   event = 'shop_detail_show'
    group by enter_id
) a
left join (
    select  enter_id, event
    from    log_table
    where   event in ('product_card_show', 'product_card_click', 'shop_comment_show')
    group by enter_id, event
) b on a.enter_id = b.enter_id
group by a.enter_id
;
```

问题出在 `time` 这个字段。

当 `event = 'shop_comment_show'` 时，代码想取的是评价曝光的时间。但 `time` 没有带表别名，最终被解析成了 `a.time`——也就是门店详情页曝光的时间。

一行代码，连锁错误。

在一坨不是自己写的SQL里一层层定位到这个问题，需要的是**细致、耐心、以及一种对"不对劲"的直觉**。

---

## 二、AI帮不上忙的时刻

实习生告诉我，他试过两种方法：

1. 不停看SQL、改SQL、跑数据，循环往复
2. 问数据平台自带的AI，但效果甚微

这让我想起一个比喻：**AI是GPU，人是CPU**。

GPU擅长并行计算，能同时处理成千上万个简单任务。AI也是如此——它能生成代码、解释概念、提供多种解法，在"宽度"上令人惊叹。但它无法替代CPU的串行深度：单线程的细致追踪、在混乱中保持清醒、对细微异常的敏感。

排查数据差异，需要的恰恰是CPU的工作方式：
- 明确差异字段是哪个
- 找到可关联的明细场景
- 没有就继续往上游追溯
- 随机抽样3~5个异常ID
- 反查数据源，定位是哪几个过滤条件导致不一致
- 一层层排查，直到找到差异点

这个过程无法并行，无法"批量生成"。**它要求你一次只做一件事，但把每一件事做到极致**。

AI可以给我10种可能的排查思路，但它无法替我决定：哪一个字段值得深究，哪一个异常样本具有代表性，哪一层数据是最可信的参照物。这些判断，来自于对业务的理解、对数据流的经验、以及一种无法被训练的直觉。

---

## 三、GPU很贵，CPU才是本体

Claude Code 120刀/月。ChatGPT Plus 20刀/月。各种API调用，token如流水。

**AI是昂贵的附加设备。**

就像游戏玩家花大价钱买顶级显卡，但如果CPU不够强，显卡只能空转。AI也是如此——它能把你的效率提升10倍，但前提是你知道要做什么。如果你自己都不清楚问题的边界，AI只会给你一堆看似合理但离题万里的答案。

人（CPU）始终是主要工具。

这不是贬低AI。恰恰相反，正因为AI足够强大，我们才更需要搞清楚：什么是它做不到的？什么是必须人来完成的？两者的边界在哪里？

在这个SQL问题里，AI可以帮我重写这段代码，让它更规范、更易读。但它无法告诉我：**这段代码里的 `time` 到底该属于哪个表**。这个判断，需要对业务的理解、对数据血缘的熟悉、以及一种"这里好像不太对"的直觉。

**AI负责生成，人负责判断。**

## 尾声

麦克卢汉说"媒介即按摩"。

AI也是一种媒介，它在按摩我们的思维方式——让我们习惯快速获取答案，习惯用自然语言描述问题然后等待生成，习惯把思考的部分环节外包出去。

但周末的这个下午提醒我：**有些问题，无法被按摩解决**。

它们需要人亲自下场，一行行看代码，一个个查样本，一点点缩小范围。这个过程没有捷径，也没有并行加速。它需要的是耐心、细致、以及一种"我必须亲自搞清楚"的决心。

AI是GPU，人是CPU。两者配合，才能发挥最大效能。

但如果只能留一个——我选择CPU。因为它才是那个决定"我们要去哪里"的角色。
