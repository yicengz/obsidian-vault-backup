# Prompt

我想写一篇微信公众号，文章的标题是：【数仓工作分享】实习生终于向我求助了  

起因是近期有一个分析师的需求，需要数仓复刻一段产品日报背后的计算逻辑，来关联额外的信息去支持更丰富的AB实验指标组。
产品日报再2025Q4由他人临时支持，SQL写得可阅读性、可维护性都不是很高。而这个需求我就交给了实习生小朋友来完成。

其中一个指标在最终计算出来的数值，一直和日报对不上。而在我这两天的多次追问下，实习生也终于向我求助：我们晚上一起看看问题吧。其实我当时听到这句话，内心还是挺高兴的。因为我秉持着不过多干预他的想法，在首次提问需求进展如何的时候，也没有过多追问，他也表示自己可以解决。

但是，一周之后我发现还有一个指标对不上（是差异极度夸张的时候），我还是决定下场干预一下。

SQL的具体实现就不在这里具体展开了。我提炼一段核心的错误内容
``` sql
-- enter_id 商家/门店详情页进入唯一ID
select  a.enter_id
	,   min(if(event = 'shop_comment_show', time, null)) as shop_comment_show_earliest_time
from (  -- 框定本次统计范围
	select  enter_id
		,   min(time) as time
	from    log_table                  -- 流量表
	where   event = 'shop_detail_show' -- 门店详情页曝光
	group by
			enter_id
) a
left join (
	select  enter_id, event -- 用户行为
	from    log_table                -- 流量表
	where   event in ('product_card_show', 'product_card_click', 'shop_comment_show')
			-- 商品卡曝光 商品卡点击 门店评价曝光 ...
	group by
			enter_id, event -- 用户行为
) b
	on  a.enter_id = b.enter_id
group by
		a.enter_id
;
```

最终导致评价曝光时间字段，取到的实际是门店详情页曝光时间。到之后了后续的一系列错误，在一坨不是自己写的SQL里一层层定位到具体的问题，需要的是细致、耐心。

而实习生面对数据不准的操作，分为两个
1. 不停看SQL、修改SQL、跑统计数据，分析问题出在哪里
2. 问数据平台自带的AI，但效果甚微

我的思路是
1. 明确有差异的字段是哪个，然后找到可以针对明细id关联的场景。如果没有，就继续往上游追溯
2. 找到两个数据源有差异的明细id，随机抽样3~5个。反查数据源，是哪几个过滤条件导致了两遍结果不一致
3. 以这样的方式一层层追溯，一定能找到差一点

我最后为他整理了三点重要信息，这其中包含了问题的排查思路以及开发习惯
1. 数据比对有差异，去查明细
2. 查明细的前提，是需要保留中间过程
3. 字段的表别名，都带上。本次如果明确了time的表别名，就会在SQL解析阶段发现问题

我结合实习生的性格，分析了下他不愿意向我求助的可能原因
1. 他是一个话少，想得很多的人
2. 他期望自己可以来解决问题
3. 他担心暴露问题会影响我或leader对他的评价
4. 每个人都很忙，他也不想麻烦我（春节前后我假装很忙，最近是真忙）

我其实和他强调过几次
1. leader对你挺满意的
2. 要及时暴露风险，不然出了问题我也很难帮你
3. 知错、认错、改错；惟以改过为能，不以无过为贵
