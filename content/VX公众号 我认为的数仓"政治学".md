# **在数字背后做判断**

## **前言｜两种不同的流畅**

春节前后，我第一次比较系统地使用 Claude Code 写前后端代码。那种体验确实让人惊讶。需求描述得足够清楚，它可以快速补全结构、接口、异常处理。改动之后，反馈也很直接。

但在这之前，我其实已经在公司内部的数据平台上尝试过用 AI 开发数仓任务。

当需求文档写得足够清晰、逻辑也不复杂时——比如一个单任务的统计计算

``` sql
select a, b, c, count(1)
from ...
group by a, b, c
```

这种场景下，效果是不错的。生成准确，修改也顺畅。

真正开始出现落差，是当任务不再孤立存在。

当一个需求牵涉到指标口径、历史一致性、上下游依赖时，生成仍然很快，但确认却慢了下来。我开始反复核对：这个逻辑是否和现有口径一致？是否影响其他任务？是否会在某个下游报表中体现为波动？

那种差异感很明显。

我和ChatGPT聊了聊，得出一个结论：相比前后端代码实现功能，数仓代码在承载语义。虽然都叫“代码”，但它们不太一样。

---
## **一、被固化的语义**

我喜欢用 `最近活跃用户数` 来举例，因为“最近”、“活跃”这两个抽象的文字表述，可以展开很多。

它看似只是一次去重统计，但背后往往包含很多前提：“最近”是多久，用户做了哪些行为可以被定义“活跃”，是否过滤被风控账号，若考虑用户下单是否排除某些特殊订单。

这些细节很少会完整写在文档里。大部分时候，它们存在于团队共识中，存在于过去一个个交付的 SQL 里。

当一个口径在多个任务中被复用，它就逐渐稳定下来，反而成为了一种共识，可以被自圆其说的共识。后来的人接手时，看到的是结果，而不是当初讨论的过程。

在这种语境下，让 AI 生成 SQL 并不算太难，难的是确认它是否符合这套隐含的历史语义。

---

## **二、链路与信任**

数据系统天然是一张网。

一个字段从明细层流转到汇总层，再进入宽表或报表层。一个指标的变化，很少只影响一个任务。它可能在不同维度、不同系统中留下痕迹。

在我和ChatGPT之前的沟通力，它提到过“数据政治学”这个说法。我一开始觉得有点夸张，但后来想想还蛮贴切的。

数据仓库并不是孤立的技术系统，它处在组织结构的中间。不同部门依赖同一套数字做判断，有些指标还会和绩效、预算甚至对外沟通挂钩。

在这种环境里，数仓的“保守”其实是一种自然反应。

不是不愿优化，而是每一次调整，都可能改变别人理解业务的方式。

相比之下，前后端更容易试错，试错成本也更小一些（我是这么理解的）。页面问题可以迅速修复，接口异常也会即时暴露。

数仓的问题往往延迟显现，而且一旦影响核心指标，恢复信任的成本远高于修复代码。

新人在前后端犯错，影响范围通常有限；新人在数仓里改动核心逻辑，风险更难预估。

这种差异，本质上来自责任结构的不同。

---

## **三、生成之外，更重要的工作**

对于逻辑简单、结构清晰的单任务计算，AI 在数仓场景的 vibe coding 效果我目前觉得处于勉强能用。

但数仓的复杂性并不主要来自语法，而来自关系。

真正耗费精力的，往往是这些问题：
- 这个任务依赖哪些上游表？他们的常规产出是几点，需求方是否能接受这个时间
- 下游有哪些任务或报表引用它？迭代后是否会影响现有字段和产出时间
- 需求文档是否完整记录了约束条件？大概率没有完整记录

当我回过头看，我们或许不应该把重心只放在“自动生成 SQL”上。

如果能先把链路梳理清楚，把指标定义结构化，把依赖关系透明化，本身就是巨大的提升。

对数据平台的设计来说，也许更现实的方向，是：
- 自动给出任务影响范围
- 提示潜在依赖冲突
- 比对口径变更前后的差异

与其让工具直接替我们写完整逻辑，不如先让它帮助我们看清系统。

当生成变得容易，解释反而更重要。
当执行成本降低，责任的边界会被放大。

这句话在数仓里显得格外真实。

---
## **四、行业变化与个人位置**

从行业视角看，写 SQL 本身的门槛正在下降。从早期的Java编写MapReduce，

重复性高的开发工作会逐渐减少。

但数据工作的核心并没有因此变轻。

对语义的理解、对链路的掌握、对口径一致性的维护，这些反而会成为更重要的能力。

如果说前后端更多在创造功能，数仓更像是在维护组织对现实的理解方式。

它既是技术系统，也是信任系统。
工具会改变效率，但不会替人承担判断。

对个人来说，这或许也是一种提醒。

写 SQL 是技术能力；定义口径，需要判断；而在数据系统里，最终要对结果负责。

---
## **尾声｜慢下来的一部分**

回头看那种前后端生成代码的流畅感，我依然觉得它代表了某种方向。工程的边界在被推高，这是毋庸置疑的。

但数仓的节奏似乎不会因此完全同步。

它可能依旧慢一些，也谨慎一些。

不是因为落后，而是因为它处在更复杂的关系网络里。

数据本身不会表达立场。

真正赋予它意义的，是背后做判断的人。

在数字背后做判断，这件事目前还离不开人。

也许未来工具会越来越强，但责任的重量，大概不会变轻。

# 草稿 - 思路整理 & AI沟通

> [!prompt]
> claude code在生成前后端代码的能力上非常厉害。那么数据仓库的HiveSQL生成，你觉得和前后端代码的生成有什么相似之处和区别呢？
> 我们公司目前的数据平台，也在开发相关的AI coding能力，但我觉得距离claude code指哪打哪的差距还非常大。我先来说说我的观点，数仓HiveSQL的生成相比于前后端
> 1. 它需要更多上下文和文档去理解。比如对于一个原子指标可以孵化出多个衍生指标（添加无数个修饰词），那用户到底期望的是哪个？这个需要有更为清晰的prompt和详细的文档沉淀。
> 2. 数仓的链路可能非常长，DAG前后会有十多个任务。假设一个尾部任务A的迭代，需要上游任务B改造。但任务B改造后又会影响到其他下游任务C、D、E。这个时候就不是简单的改任务了，还是需要对整个数据链路作出非常大的改动评估。
> 3. 数仓的HiveSQL更新后，不能像前后端（尤其是前端）那样马上验证效果
> 	1. 前端代码变更后，页面上马上可以看到变更后的效果
> 	2. 后端代码变更后，可以让AI创造一个测试数据/用例，来看看具体效果如何
> 	3. 数仓代码变更后，需要花十几分钟，甚至一个小时先执行任务。然后比对修改前后的差异。如果有差异，可能是一个统计指标相差了1%，AI要继续去寻找差异；也可能是前后的明细数据量有差异，但可能是符合预期的，需要由人来判断。毕竟AI负责执行，人给出指令和抗起责任
> 你看看你有没有什么想补充的，我觉得我说得应该不完全准确，一定有遗漏的地方。

## **创造功能 vs 创造信任**
> **数仓AI的容错率要远低于前后端AI**，因为数仓的产出不只是功能，而是数据的可信度。
- 前后端写错了，用户骂两句修一下就好
- 但数仓一次指标错误，业务对数据团队失去信任之后，往后每次都会怀疑

## **数仓AI的方向**
> 基于以上分析，我个人觉得数仓AI最值得切入的方向，不是端到端的SQL生成，而是：
- 第一，**影响分析优先于代码生成**。改一个字段影响哪些任务，改一个指标影响哪些报表，这比写SQL更有杠杆价值，也更容易建立用户信任。
- 第二，**把指标语义结构化**。你说的原子指标孵化衍生指标的问题，解法不是让AI猜用户意图，而是把修饰词、统计周期、去重口径做成结构化语义树，AI在这个树上做约束组合，而不是自由生成SQL。
- 第三，**做"差异解释AI"而非"差异发现AI"**。当改动后GMV差了1%，AI不只告诉你差了多少，而是告诉你差异集中在哪些维度、哪些商户、是否来自时间窗口变化。这才是真正能替代人工排查的部分。
