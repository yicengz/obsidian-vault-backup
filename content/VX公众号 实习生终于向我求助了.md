> 在这个 AI 正在进入、重塑、甚至取代很多工作的当下，有知有行当然也在全力拥抱 AI。 
> 但另一方面，我们比以往任何时候都更相信「人」的价值。 —— 有知有行创始人 孟岩

这两天一直在想，人和 AI 后续到底该怎么相处。

人是像 CEO 那样想清楚之后，把"体力型的脑力劳动"交给 AI 去跑？还是像《西游记》里的唐僧和猪八戒，被白骨精和六耳猕猴耍得团团转，压根分不清眼前哪个是真的？

这周发生的一件小事，让我对这个问题有了更具体的感受。

本周某天，实习生用了数据开发平台内置的 AI、也自己反复排查之后，最终还是没搞清楚：两边的数据，到底为什么不一致？在我多次追问之后，他发来一句话："我们一起看看这个问题吧。"

我当时听到，其实挺高兴的。

---

**起因**

Q4 有段时间，产品日报由别人临时支持，SQL 写得比较随意，可读性和可维护性都一般。春节前后，一个分析师提了需求：把日报背后的一部分计算逻辑复刻出来，关联额外的信息，用来支持更丰富的 AB 实验指标组。

我把这个任务交给了实习生。

需求本身不算复杂，核心是在一段"别人写的 SQL"里读懂逻辑，然后重新实现。我的想法是不过多干预，让他自己摸。第一次问进展，他说没问题，自己能搞定。我也没再追。

一周后，我发现有个指标的数值差异大得离谱。觉得不能再等，开始多次追问——然后，他终于开口了。

---

**问题在哪里**

核心的错误，浓缩下来是这样一段 SQL：

sql

```sql
-- enter_id 商家/门店详情页进入唯一ID
select 
    a.enter_id,
    min(if(action = 'shop_comment_show', time, null)) as shop_comment_show_earliest_time
from (
    select 
        enter_id,
        min(time) as time
    from    log_table
    where   action = 'shop_detail_show'
    group by enter_id
) a
left join (
    select  enter_id, action
    from    log_table
    where   action in ('product_card_show', 'product_card_click', 'shop_comment_show')
    group by enter_id, action
) b
    on  a.enter_id = b.enter_id
group by a.enter_id;
```

-- enter_id 商家/门店详情页进入唯一ID
select 
    a.enter_id,
    min(if(action = 'shop_comment_show', time, null)) as shop_comment_show_earliest_time
from (
    select 
        enter_id,
        min(time) as time
    from    log_table
    where   action = 'shop_detail_show'
    group by enter_id
) a
left join (
    select  enter_id, action
    from    log_table
    where   action in ('product_card_show', 'product_card_click', 'shop_comment_show')
    group by enter_id, action
) b
    on  a.enter_id = b.enter_id
group by a.enter_id;

看出来了吗？

`min(if(event = 'shop_comment_show', time, null))` 里的 `time`，没有带表别名。

子查询 a 里有个 `time`（门店详情页曝光时间），子查询 b 里没有 `time`。SQL 解析器在聚合阶段，就顺手用了 `a.time`——门店详情页曝光时间。

于是，"评价模块曝光时间"这个字段，实际取到的是"进入详情页的时间"。后续一系列指标在这个错误上层层叠叠，越跑越离谱。

大多数被最终排查出来的数仓 SQL 问题，事后回头看都会感叹一句"就这？"——但它藏在一段不是自己写的代码里，藏在多层嵌套和 join 之间，找起来需要的是细致，和耐心。

---

**他的排查方式 vs 我的排查方式**

他的做法：反复看 SQL，反复改，反复跑聚合结果，试图从整体数值的差异里猜出问题在哪里。中途也问了数据平台内置的 AI，但效果甚微——AI 能看懂语法，但它不知道你的业务，不知道这两张子查询的字段背后意味着什么。

我面对这种场景，思路一直是反向追溯：

1. 先锁定是哪个字段有差异
2. 找到能按明细 ID 对齐的切入点，把两个数据源的明细行拉出来
3. 随机抽 3～5 个差异 ID，反查上游——是哪个过滤条件、哪个字段导致了两边不一致

这样一层层往上追，一定能找到那个"差一点"。

排查完之后，我给他整理了三条：

**一、数据有差异，去查明细，不要只盯聚合。** 聚合数值告诉你结果不对，明细才能告诉你哪里不对。

**二、查明细的前提，是保留中间过程。** 没有中间层，排查就是在黑箱里摸索。

**三、字段的表别名，都带上。** 这个习惯如果从一开始就有，这个 bug 在 SQL 写完的那一刻就会被发现，根本不会拖到数据比对阶段。

---

**他为什么不愿意开口**

我想了想，大概几个原因叠在一起。

他是个话少、但想得很多的人。他希望自己能独立解决——这本是好事，但有时候会变成一种执念。他大概也有点担心，暴露问题会影响我或 leader 对他的评价。加上春节前后我在假装很忙，最近是真忙，他也不想打扰。

我其实和他说过几次：leader 对你现在的状态是满意的。要及时暴露风险，出了问题我才能帮你，藏着只会让事情越来越难收。知错、认错、改错——"惟以改过为能，不以无过为贵"。犯错不丢人，但能改才是真的成长。

道理他都懂。但真正让他开口的，还是那几天我持续的追问。有时候，人需要一个被推一把的理由。

---

**AI 为什么没帮上忙**

他问过 AI。AI 给了一些建议，但没找到问题。

为什么？

因为 AI 看到的是代码，看不到业务。它不知道 `shop_comment_show_earliest_time` 在这个产品里代表什么，不知道这个数字跑出来之后要去跟哪张日报对，不知道差异有多离谱。它能检查语法，能推测逻辑，但它没有上下文——没有那个"这里不对劲"的直觉。

这让我想到一个比喻：CPU 和 GPU。

CPU 是通用处理器，擅长串行的、依赖上下文的、需要判断的任务；GPU 是并行加速器，擅长大规模、结构化、重复的计算。两者分工不同，少了哪个效果都会打折。

人在数据工作里更像 CPU：掌握业务语义，理解"这个数字为什么不对"，能在模糊线索里做出判断，能在追溯链条断掉的地方凭经验往前走。AI 更像 GPU：在已知结构里快速检索、生成、补全。

当问题是"SQL 里有个字段别名歧义导致取了错误的 time"，且这个问题藏在一段陌生的、多层嵌套的、业务上下文未知的代码里——这时候，GPU 再强，也替代不了 CPU 的作用。

这不是说 AI 没用。它在生成、补全、检索上确实省了很多时间。但它是昂贵的附加设备——极度消耗 token，极度依赖输入质量——在当下，它最好的使用姿势，是被人驾驭，而不是替代人。

---

**最后**

实习生最终还是开口了。

问题找到了，改掉了，数据对上了。

我没有批评他拖了一周。他知道问题在哪，知道下次怎么做，这就够了。

有些话说一遍，不如经历一次。
