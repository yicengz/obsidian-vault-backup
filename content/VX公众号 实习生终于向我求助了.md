> 在这个 AI 正在进入、重塑、甚至取代很多工作的当下，有知有行当然也在全力拥抱 AI。 
> 但另一方面，我们比以往任何时候都更相信「人」的价值。
> —— 有知有行创始人 孟岩

这两天也一直在想，人和AI在后续如何相处。

人是像CEO那样深思熟虑并做好决策后，将"体力型的脑力劳动"交给AI完成
还是像

"我们晚上一起看看问题吧。"

他发来这句话的时候，我当时其实挺高兴的。

## **起因**

Q4有段时间，产品日报由别人临时支持，SQL写得比较随意，可读性和可维护性都一般。春节前后，一个分析师提了个需求：把日报背后的一部分计算逻辑复刻后，关联额外的信息，用来支持更丰富的AB实验指标组。

我把这个任务交给了实习生。

需求本身不算复杂，就是在一段"别人写的SQL"里找到逻辑、然后重新实现。我的想法是不过多干预，让他自己摸索。第一次问进展，他说没问题，自己可以搞定。我也没追。

一周之后，我发现有个指标数值差异大得离谱。我意识到不能再等了，于是开始多次追问——然后，他终于开口了。

## **问题在哪里**

核心的错误，浓缩下来是这样一段SQL：

```sql
-- enter_id 商家/门店详情页进入唯一ID
select 
    a.enter_id,
    min(if(event = 'shop_comment_show', time, null)) as shop_comment_show_earliest_time
from (
    select 
        enter_id,
        min(time) as time
    from    log_table
    where   event = 'shop_detail_show'
    group by enter_id
) a
left join (
    select  enter_id, event
    from    log_table
    where   event in ('product_card_show', 'product_card_click', 'shop_comment_show')
    group by enter_id, event
) b
    on  a.enter_id = b.enter_id
group by a.enter_id;
```

看出来了吗？

`min(if(event = 'shop_comment_show', time, null))` 里的 `time`，没有带表别名。

子查询 a 里有个 time（门店详情页曝光时间），子查询 b 里没有 time。SQL解析器在 group by 之后的聚合阶段，直接用了 a.time——门店详情页曝光时间。

于是，"评价模块曝光时间"这个字段，取到的实际上是"进入详情页的时间"。后续一系列指标在这个错误基础上层层叠叠，越跑越离谱。

大部分被排查到的数仓SQL问题，最后常会感叹“这不复杂啊”。但它藏在一段不是我写的SQL里，藏在多层嵌套和join里，找起来需要的是细致和耐心。

## **他的排查方式 vs 我的排查方式**

他的做法是：反复看SQL，反复改，反复跑聚合结果，试图从整体数值的差异里猜出问题在哪里。中间也问了数据平台自带的AI，但效果甚微——AI能看懂语法，但以现在内部的数仓AI，它不知道你的业务逻辑，不知道这两张子查询的字段意味着什么。

我面对查不出问题的场景，思路都是反向追溯：
1. 先锁定是哪个字段有差异
2. 找到可以按明细ID对齐的切入点，把两个数据源的明细行拉出来
3. 随机抽3~5个差异ID，反查上游——是哪个过滤条件、哪个字段导致了不一致

这样一层层往上追，一定能找到那个"差一点"。

最后我给他整理了三条：

**一、数据比对有差异，去查明细，不要只看聚合。** 聚合数值告诉你结果不对，明细才能告诉你哪里不对。

**二、查明细的前提，是保留中间过程。** 中间表、中间结果，不要只留最终输出。没有中间过程，排查就是在黑箱里摸索。

**三、字段的表别名，都带上。** 这条习惯如果从一开始就有，这个bug在SQL写完的那一刻就会暴露，根本不会跑到数据比对阶段。

## **他为什么不愿意开口**

我想了想，大概有这几个原因：

他是一个话少、想得很多的人。他期望自己能独立解决问题——这是好事，但有时候会变成一种执念。他或许担心暴露问题会影响我或leader对他的评价。加上春节前后我假装很忙，最近是真忙，他也不想打扰。

我其实和他说过几次：leader对你的状态是满意的。要及时暴露风险，出了问题我才能帮你，藏着只会让问题越来越大。知错、认错、改错——"惟以改过为能，不以无过为贵"。**人都会犯错，但能改错才是真的能力。**

但话归话，真正让他开口的，还是那几天我持续的追问。有时候，人需要一个被推一把的理由。

## **AI为什么没帮上忙**

这件事让我想了很多。

他问过AI。AI给出了一些建议，但没有找到问题。

为什么？

因为AI看到的是代码，看不到业务。它不知道"shop_comment_show_earliest_time"这个字段在这个产品里代表什么，不知道这个数字跑出来之后要去和哪张日报对，不知道差异究竟有多夸张。它能检查语法，能猜测逻辑，但它没有上下文——没有那个"这里不对劲"的直觉。

这让我想到一个比喻：CPU和GPU。

CPU是通用处理器，擅长串行的、依赖上下文的、需要判断的任务；GPU是并行加速器，擅长大规模、结构化、重复的计算。两者分工不同，缺一个效果都会打折扣。

人在数据工作里扮演的角色，更像CPU：掌握业务语义，理解"这个数字为什么不对"，能在模糊线索里做出判断，能在追溯链条断掉的地方凭经验往前走。AI更像GPU：在已知结构里快速检索、生成、补全。

当问题是"SQL里有个字段别名歧义导致取到了错误的time"，且这个问题藏在一段你不熟悉的、多层嵌套的、业务上下文未知的代码里——这个时候，GPU再强，也替代不了CPU的作用。

这不是说AI没用。AI在辅助生成、补全、检索方面确实省了很多时间。但它是**昂贵的附加设备——极度消耗token，极度依赖输入的质量**——在当下，它最好的使用姿势，是由人来驾驭它，而不是替代人。

**最后**

实习生最终还是开口了。

问题找到了，改掉了，数据对上了。

我没有批评他拖了一周。他知道问题出在哪，知道下次怎么做，这就够了。

有些事不用说太多。
